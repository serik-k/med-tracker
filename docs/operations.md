# Operations runbook

Документ задаёт минимальную эксплуатационную основу. Конкретные RTO, RPO, сроки хранения, контакты и порядок уведомлений организация должна утвердить до обработки реальных данных пациентов.

## Контуры и ответственность

- PostgreSQL хранит организации, пользователей, сессии, бригады, вызовы и audit logs.
- Volume `medtracker-data` хранит фотографии доступа и, только в development, legacy JSON.
- Nginx обслуживает SPA и проксирует `/api` и `/socket.io` в backend.
- Geocoding, OSRM и map tiles являются внешними зависимостями, если не развёрнуты собственные сервисы. Production требует явные approved endpoints; browser получает тайлы через backend proxy.

Назначьте владельцев для приложения, БД, инфраструктуры, информационной безопасности и обработки персональных данных. Зафиксируйте круглосуточный канал эскалации.

## Предпусковой checklist

- все `REPLACE_WITH_*` заменены уникальными секретами;
- `.env` не находится в Git, доступен только deploy-пользователю и резервируется отдельно от данных;
- TLS настроен, HTTP перенаправляется на HTTPS, backend и PostgreSQL не опубликованы наружу;
- `CORS_ORIGIN` содержит только реальные HTTPS-origins;
- доверенные proxy и очистка `X-Forwarded-*` проверены;
- geocoding/routing/tile endpoints заменены на согласованные provider или собственные сервисы, а их лимиты и условия приняты;
- backup PostgreSQL и photo volume выполнен, тестовое восстановление успешно;
- определены RPO, RTO, retention и контакты incident response;
- пройдены функциональные, нагрузочные, accessibility и отказоустойчивые проверки.

## Healthchecks и мониторинг

| Проверка | Значение | Ожидаемый ответ |
|---|---|---|
| frontend `/healthz` | Nginx принимает трафик | HTTP 200 `ok` |
| backend `/health/live` | процесс Node.js жив | HTTP 200 |
| backend `/health/ready` | storage готов | HTTP 200; во время старта/остановки 503 |
| backend `/health` | сводное состояние | HTTP 200 или 503 |

В Compose backend не опубликован на host: его healthcheck выполняется внутри контейнера. Для внешнего мониторинга публикуйте только согласованный endpoint через TLS-proxy либо используйте container health.

Рекомендуемые алерты:

- любой unhealthy/restart-loop контейнера;
- рост HTTP 5xx, latency и ошибок Socket.IO;
- отсутствие свежих координат активной бригады;
- исчерпание диска, memory, CPU, PostgreSQL connections и volume с фото;
- ошибки миграций и backup jobs;
- всплеск неуспешных login/SOS или недоступность внешних routing/geocoding providers.

Не записывайте в логи токены URL, legacy path фотографий доступа, map-tile координаты `z/x/y`, пароли, симптомы, телефоны, адреса или содержимое фото. Bundled Nginx отключает access log для чувствительных paths, но такую же редакцию нужно отдельно настроить на TLS edge/CDN/WAF/APM. Ограничьте доступ к логам и настройте их срок хранения. Compose ограничивает локальные JSON-логи пятью файлами по 10 MB; централизованный сбор настраивается отдельно.

## Deployment

Перед каждым обновлением:

1. прочитайте изменения схемы и release notes;
2. сделайте согласованную резервную копию БД и photo volume;
3. проверьте восстановление на изолированном стенде;
4. выполните `docker compose --env-file .env config`;
5. соберите образы и прогоните CI-проверки;
6. запустите `docker compose --env-file .env up -d --build`;
7. дождитесь healthy-состояния и выполните smoke test ролей, realtime, GPS, SOS и завершения вызова.

Сервис `migrate` завершается до запуска backend. Он единственный получает `DATABASE_ADMIN_URL`; runtime backend работает через роль `medtracker_app`.

Миграции считаются forward-only. Откат приложения после несовместимой миграции выполняйте только по заранее протестированному плану. Не восстанавливайте старую БД поверх рабочей без остановки записи и подтверждения ответственного.

## Backup и восстановление

Полная резервная копия включает одновременно:

1. PostgreSQL (`pg_dump` в custom format либо snapshot с гарантией консистентности);
2. volume `medtracker-data` с `/app/legacy-db/uploads`;
3. зашифрованную копию production-конфигурации/секретов в утверждённом secret manager;
4. версии образов и миграций, соответствующие backup.

Практика:

- выполняйте backup автоматизированной учётной записью с минимальными правами;
- шифруйте данные при передаче и хранении;
- храните копию в отдельном failure domain;
- проверяйте checksum и результат job;
- регулярно восстанавливайте в изолированную БД и проверяйте вход, вызовы, audit logs и фото;
- фиксируйте фактические RPO/RTO тестового восстановления.

Не считайте named volume резервной копией. Удаление `docker compose down -v` уничтожает локальные volumes и не должно использоваться в production-процедурах.

## Retention и удаление

Текущие TTL управляют доступом, а не физическим удалением:

- session — `SESSION_TTL_HOURS`;
- водительская ссылка — `DRIVER_TOKEN_TTL_DAYS`;
- пациентская ссылка — `PATIENT_TOKEN_TTL_HOURS` или завершение вызова;
- stale location threshold — `CREW_LOCATION_MAX_AGE_MINUTES`.

При завершении или отмене вызова приложение удаляет рабочий файл фото доступа из primary volume. Автоматической очистки завершённых вызовов, audit logs и уже созданных backup нет. До production определите сроки отдельно для персональных данных, геопозиции, медицинской информации, audit logs, application logs и backup. Cleanup job должен учитывать внешние ключи, tenant scope и остаточные копии; сначала испытайте его на копии и ведите отдельный audit удаления.

Legal hold и расследование инцидента должны приостанавливать обычное удаление только по утверждённой процедуре.

## Incident response

При подозрении на утечку, компрометацию токена или ошибочное межклиническое раскрытие:

1. зафиксируйте время, затронутый tenant, версии и первичные индикаторы;
2. ограничьте доступ, но не уничтожайте логи и доказательства;
3. отзовите затронутые session/driver/patient tokens и смените скомпрометированные secrets;
4. проверьте audit logs, reverse-proxy logs, БД и доступ к backup;
5. оцените категории и объём данных, временной интервал и получателей;
6. выполните обязательные уведомления по утверждённым срокам и каналам;
7. восстановите сервис из доверенной версии, усилите мониторинг и проведите postmortem.

Не публикуйте токены, PHI/PII и production-логи в issue tracker или публичный чат.

## Внешние сбои

- При недоступности geocoding нельзя создавать вызов с вымышленной/fallback-точкой: операция должна завершаться ошибкой, а диспетчер — проверить адрес и повторить запрос.
- При недоступности OSRM ETA и маршрут могут быть приблизительными; UI и операционная инструкция должны это явно показывать.
- При недоступности tile provider точки и маршрут остаются на нейтральном фоне без картографической подложки; это не должно блокировать телефонную связь и ручную навигацию.
- `wa.me` только открывает подготовленное сообщение. Отправка и доставка не подтверждаются системой; должен существовать резервный канал связи с пациентом.
- Для критичной связи предусмотрите независимую телефонию и процесс ручного диспетчерского сопровождения.
